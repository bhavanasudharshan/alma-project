## A. Public-surface security (threats → controls)

| ID | Threat | Control | Complexity | Proposed tier | Why |
|---|---|---|---|---|---|
| SEC1 | **Volumetric / DoS** on `POST /leads` and `POST /auth/login` | Per-IP rate limit (slowapi, in-memory now, Redis-ready): e.g. 5 submissions / 10 min / IP, 10 logins / 5 min / IP → 429 with `Retry-After`. Body size cap at the server (uvicorn `--limit-max-requests` is not it — enforce `max_resume_mb` before reading the body via `Content-Length` pre-check **and** the existing seek check). Request timeout middleware | low | **P1** | cheapest, most visible public-facing control; reviewers will look for it |
| SEC2 | **Malicious resume** (executable renamed .pdf, macro-laden .doc/.docx, polyglot files, PDF with JavaScript) | (a) Magic-byte sniffing (`python-magic`/`filetype`) must agree with extension + declared type; (b) drop legacy `.doc` (OLE, macro-prone) — accept `.pdf` and `.docx` only; (c) resumes are **never rendered** in the app — served as `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`; (d) private bucket, never a public URL; (e) optional ClamAV sidecar in compose (`clamav` profile) behind a `MalwareScanner` protocol with a `NoopScanner` default — a lead whose file fails scanning is stored in `QUARANTINED` state and never emailed as an attachment | (a)-(d) low, (e) medium | **P1**: a–d · **EXT**: e | a–d close the realistic vectors with ~40 lines; AV is infra and belongs in the design doc as the next step |
| SEC3 | **Prompt / agent injection** — resume or form text crafted to hijack any LLM that later reads it (AI screening, summarisation, auto-reply) | Today: no LLM touches lead data anywhere → risk is zero by construction; **state this explicitly in DESIGN.md**. Design rule for the future: lead content is always *data*, never *instructions*: extraction in a sandbox, structured output only, no tool access from the reading model, provenance tag on every field, human confirms any action. Also the low-tech cousin: **HTML/header injection into the attorney email** — prospect-supplied names are rendered in the notification; templates must escape (Jinja2 autoescape) and the subject must strip CR/LF | low (escape now, doc the rule) | **P1**: email escaping + DESIGN.md section · **EXT**: LLM-reading guardrails when an AI feature exists | the honest staff answer is "no LLM in the loop today; here is the rule for when there is" |
| SEC4 | **Abuse / spam** submissions | Honeypot field (zero UX cost) now; Cloudflare Turnstile behind a feature flag (`TURNSTILE_SITE_KEY` unset → skipped) | low | **P1**: honeypot · **P2/EXT**: Turnstile | Turnstile needs a real domain key to demo; flag keeps the reviewer run keyless |
| SEC5 | **CSRF** on the internal UI (mutations via cookie session) | Next.js server actions carry origin checks; cookie `SameSite=Lax` + `Secure` in prod; PATCH is only reachable via server action with the token from the httpOnly cookie | none (verify + document) | **P1** (verify in audit) | already in place by construction — prove it |
| SEC6 | **Browser hardening** | Security headers on both apps: CSP (self only), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, HSTS in prod; Next `headers()` config + FastAPI middleware | low | **P1** | 20 lines, standard reviewer checklist item |
| SEC7 | **Enumeration / info leakage** via the future public status page | Tracker code is high-entropy (≥128 bits, base32, not the lead id); status endpoint rate-limited and constant-time; returns state + dates only, never name/email/resume | low | tied to EXT1 | must be designed with EXT1, not bolted on |
| SEC8 | **Duplicate / replay submissions** | Idempotency: same email within N minutes → return existing lead (200) instead of creating a twin; or a client idempotency key | low | **P2** | reduces attorney noise; small |
| SEC10 | **Secrets & config management** | Today: `.env` (gitignored, never committed) for local; `.env.example` is the committed template; startup hard-fails on placeholder secrets outside `local`. Production: no secrets in files — injected at deploy from a secrets manager (Vault / AWS Secrets Manager / Doppler class) scoped per environment (dev/staging/prod), with rotation, access audit and least-privilege roles; `Settings` stays the single read surface so no code changes; non-secret config (feature flags, limits) may move to a config service. Rotate any key that has ever been pasted into a chat or terminal | low (design) · medium (infra) | **EXT** — roadmap row in DESIGN.md |
| SEC9 | **Audit trail** | `lead_events` table: who changed what state when (attorney sub, ts, from→to). Also the substrate for EXT2 and EXT3 | low-medium | **P1-lite** (table + write on state change) or **EXT** | one table that three later features need — cheapest time to add is before the schema has users |

## B. Product extensions (FR additions)

| ID | Extension | What it needs | Complexity | Proposed tier |
|---|---|---|---|---|
| EXT1 | **Submitter status portal**: prospect receives a tracking code in the confirmation email; `/status` page (public) accepts the code and shows current state + timeline | `tracking_code` column (generated at create — **add the column now in P1 even if the page is later**, so no second migration); `GET /api/v1/leads/track/{code}` (public, rate-limited, minimal fields); `/status` page; code included in prospect email | medium (~45 min) | column: **P1** · endpoint + page: **P2 or EXT** |
| EXT2 | **Status-change notifications** to the submitter (e.g. "an attorney has reached out", later QUALIFIED/DECLINED) | hook on `change_state` → `EmailService`; template per transition; only for transitions flagged `notify_prospect=True` in the transition table; this is where the **outbox** pattern becomes necessary (state change committed, email must not be lost) | medium | **EXT** (design now; the transition-table flag can be added in P1 for ~5 lines) |
| EXT3 | **Attorney assignment** (`assigned_to`) — lead is owned by one attorney; assignment manual (claim) or round-robin | `attorneys` table (replaces the single seeded account; S7 RBAC prerequisite), `assigned_to` FK, claim endpoint, filter "mine" | medium-high | **EXT** |
| EXT4 | **Internal ops dashboard**: volume and load per attorney, per week/month; trend of PENDING age; conversion PENDING→REACHED_OUT time | depends on EXT3 + SEC9 (events table); `GET /api/v1/metrics/leads?group_by=attorney&window=30d`; server-rendered charts (Recharts) or plain tables; role `admin` | high | **EXT** — design in DESIGN.md with the query shapes and the one index they need |
| EXT6 | **Optional intake fields** (phone, address, reason: new visa / renewal / PR…, urgency: 24h / <1 week / NA) | Hybrid schema rule: typed nullable columns + enums for anything filtered, sorted, joined or PII-protected (reason, urgency, phone); structured JSON for rarely-queried blobs (address); one `extra` JSON column as the escape hatch for experimental/campaign fields. Added via Alembic nullable columns → non-breaking for existing rows and clients; zod + pydantic each gain one optional field. All-JSON rejected: loses validation, indexes, dashboard queries, and PII redaction | low | **EXT** — worked example in DESIGN.md "extending the lead model"; nothing built |
| EXT5 | **Richer pipeline states** (QUALIFIED, ENGAGED, DECLINED, CLOSED) | enum + transition rows + badges; each transition may carry `notify_prospect` | low | **P2** (one or two states as the extensibility demo) |

## B2. Observability layer — APPROVED: Option C, design only (DESIGN.md §8), nothing built in the window

Principle: no new infrastructure. Product metrics are SQL over `leads` + `lead_events`; operational metrics are in-process counters exposed in Prometheus text format; access audit is one generic table. Everything is behind attorney auth (admin role later).

| ID | Axis | What it answers | Mechanism | Cost | Proposed tier |
|---|---|---|---|---|---|
| OBS1 | Product — usage & trends | submissions per day/week/month; conversion PENDING→REACHED_OUT→QUALIFIED; median time-to-reach-out | `GET /api/v1/metrics/product?window=7d\|30d` — pure SQL over `leads` + `lead_events` (group by date_trunc; percentile via ordered offset) | 20 min | **P2-lite** |
| OBS2 | Product — backlog & bottlenecks | PENDING count and age buckets (<24h, 1–3d, >3d); oldest untouched lead; per-attorney load once EXT3 exists (today: single attorney, so "per actor" from `lead_events.actor`) | same endpoint, `backlog` block | 10 min | **P2-lite** |
| OBS3 | Product — internal dashboard page | `/dashboard` (internal, cookie-guarded): stat tiles (today/7d/30d, backlog, median TTR), backlog age table, 30-day submissions bar chart (plain SVG/CSS bars — no chart library) | server component over OBS1/2 | 25 min | **P2-lite** |
| OBS4 | Ops — performance | request count / latency histogram / error rate per route; in-flight requests | `prometheus-fastapi-instrumentator` (one dep) → `GET /metrics` (Prometheus text; gated to internal network or Bearer in non-local) | 10 min | **P2-lite** |
| OBS5 | Ops — security flags | counters: `auth_login_failures_total`, `rate_limited_total{route}`, `upload_rejected_total{reason=type\|size\|sniff\|honeypot}`, `state_transition_conflicts_total`, `tracking_lookups_failed_total` | custom Prometheus counters incremented at the existing rejection points; also emitted as structured log lines with request-id | 15 min | **P2-lite** |
| OBS6 | Ops — access audit | who did what: login success/fail (email, ip, ua), résumé download (lead id, actor), state change (already in `lead_events`), tracking lookups (code hash, ip) | `audit_events` table (id, ts, actor, action, target_type, target_id, ip, request_id, meta JSON) written by a small `audit()` helper; `GET /api/v1/audit?limit=` internal; retention policy stated | 20 min | **P2-lite** (table + writes) · UI list **EXT** |
| OBS7 | Ops — upload metrics | size distribution, type mix, reject reasons, storage backend latency | histogram + counters from OBS5 + a `storage_save_seconds` histogram around `FileStorage.save` | 5 min (with OBS4/5) | **P2-lite** |
| OBS8 | Alerting & dashboards | Grafana/Prometheus compose profile `obs` with a provisioned dashboard JSON; alert rules (backlog age > 3d, error rate > 2%, login failures spike) | infra | **EXT** — documented with the exact PromQL |
| OBS9 | Tracing | OpenTelemetry spans across Next → FastAPI → DB/S3/email | infra + SDK | **EXT** |

Full P2-lite ≈ **105 min** of agent time — too much for the remaining window alongside the approved P2 features. Two cut-downs:
- **Option A — "metrics + dashboard" (≈55 min)**: OBS1, OBS2, OBS3, OBS4. Product visibility that is easy to demonstrate; ops latency/error metrics for free. Security counters and audit table → EXT.
- **Option B — "ops + audit" (≈50 min)**: OBS4, OBS5, OBS6, OBS7. Strong security/production story; product dashboard → EXT.
- **Option C — everything as designed-not-built**: DESIGN.md §8 Operability gets the full table above with the PromQL and SQL shapes; 0 min.

## C. What this means for the 6-hour clock (honest view)

- P1 as approved today is ~1.5 h. Adding SEC1, SEC2 a–d, SEC3 escaping, SEC4 honeypot, SEC6, SEC9-lite, EXT1 column ≈ **+45 min** of agent time. That is affordable if the frontend lands on schedule; it comes out of the stretch buffer, not out of P2 docs.
- EXT1 endpoint + page, EXT2, EXT3, EXT4 are **not** affordable in the window without cutting documentation, and the documentation is part of the deliverable. They belong in DESIGN.md as a designed roadmap with schema, API and the one hard problem each (outbox, RBAC, aggregation index) — knowing what not to build today is part of the design.
- If after P2 there is ≥45 min, the order of value is: EXT1 page (visible, public, demo-able) → EXT5 one extra state → Railway demo.
